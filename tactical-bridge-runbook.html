Tactical Bridge Runbook

The same shaped, flooded link from the base runbook, now carrying a second pipeline: video bridged through two Solace PubSub+ brokers. Run both at once and the flood hits them identically — one freezes for good, the other stalls and catches up.

Builds on Tactical Link Runbook and Tactical Relay Diagrams. The base runbook's VPC, subnets, routing, and shaper are reused as-is — nothing there gets rebuilt.

Objective
Run direct UDP and a Solace-bridged path side by side over the same link; show one freeze permanently and the other recover.

00Provision (deltas only)

Everything in the base runbook's Phase 00 — the VPC, three subnets, security group — stays exactly as built. Two things change before you launch.

Delta 1 — instance size A broker JVM running alongside ffmpeg, InputProxy/OutputProxy, and iperf3 needs more headroom than the base demo did. Launch source and receiver as t3.medium instead of t3.small. The shaper stays t3.small — it never runs Java or Docker, only tc.

If the base runbook's instances are still running, the fastest path is to terminate just $INSTANCE_SRC and $INSTANCE_RCV and relaunch them with the bumped instance type, reusing the same subnets, security group, and AMI lookup already captured in your shell environment.

local $
launch() { aws ec2 run-instances --image-id $AMI_ID --instance-type t3.medium \
  --key-name $KEY_NAME --subnet-id $1 --security-group-ids $SG_ID \
  --tag-specifications "ResourceType=instance,Tags=[{Key=Name,Value=$2}]" \
  --query 'Instances[0].InstanceId' --output text --region $AWS_REGION; }

export INSTANCE_SRC=$(launch $SUBNET_SRC dil-source)
export INSTANCE_RCV=$(launch $SUBNET_RCV dil-receiver)
aws ec2 wait instance-running --instance-ids $INSTANCE_SRC $INSTANCE_RCV --region $AWS_REGION
Delta 2 — extra packages Source and receiver both need Docker (to run a broker) and a JDK (to build and run BroadcastMe). Neither is needed on the shaper.
source + receiver $
sudo apt-get update
sudo apt-get install -y docker.io openjdk-17-jdk git
sudo usermod -aG docker $USER
# log out and back in (or `newgrp docker`) for the group change to take effect
01Route + shape (unchanged, one number)

The route-forcing trick from the base runbook's Phase 01 is untouched — re-run it if you relaunched the source/receiver instances, since new instances get new ENIs. The only change is the shaper's bandwidth cap.

local $
export IP_SRC_PRIV=10.0.1.x   # from describe-instances
export IP_RCV_PRIV=10.0.3.x

aws ec2 create-route --route-table-id $RTB_SRC --destination-cidr-block ${IP_RCV_PRIV}/32 \
  --network-interface-id $ENI_SHAPE --region $AWS_REGION
aws ec2 create-route --route-table-id $RTB_RCV --destination-cidr-block ${IP_SRC_PRIV}/32 \
  --network-interface-id $ENI_SHAPE --region $AWS_REGION

256 kbit was sized for one video stream. Running the direct path and the Solace path at once means two video-bearing flows sharing the pipe before the flood even starts — at 256 kbit they'd starve each other and muddy the demo. Raise the ceiling so the flood, not ordinary contention, is what causes the freeze:

shaper $
sudo tc qdisc add dev eth0 root handle 1: htb default 10
sudo tc class add dev eth0 parent 1: classid 1:10 htb rate 768kbit ceil 768kbit
sudo tc qdisc add dev eth0 parent 1:10 handle 10: netem \
  delay 100ms 20ms distribution normal loss 2% 25%
Why 768 kbit Two ~200 kbit video streams plus SMF framing overhead on the Solace path comfortably fit under 768 kbit with room to spare. The iperf3 flood in Phase 07 is sized to blow well past that ceiling, so it stays the obvious cause of the freeze rather than ordinary bandwidth-sharing.
02Stand up two brokers

One Solace PubSub+ Standard broker on the source instance, one on the receiver instance — each reachable locally by its own proxy, and reachable to each other across the shaped link for the bridge in Phase 03.

source $
docker run -d --name broker-a --shm-size=2g --restart unless-stopped \
  --env username_admin_globalaccesslevel=admin \
  --env username_admin_password="${BROKER_ADMIN_PASS}" \
  -p 55555:55555 -p 8080:8080 \
  solace/solace-pubsub-standard
receiver $
docker run -d --name broker-b --shm-size=2g --restart unless-stopped \
  --env username_admin_globalaccesslevel=admin \
  --env username_admin_password="${BROKER_ADMIN_PASS}" \
  -p 55555:55555 -p 8080:8080 \
  solace/solace-pubsub-standard

Give the container a minute to finish booting, then check each broker's own Broker Manager rather than opening a new security-group hole for port 8080 — tunnel it over the SSH connection you already have:

local $
ssh -L 8080:localhost:8080 ubuntu@<source-public-ip>
# then open http://localhost:8080 — log in as admin/admin
Watch for Confirm the container's default message-vpn is enabled for client connections before moving on — if guest/anonymous access is off in your image version, create a client username in the Broker Manager (VPN → Client Usernames) rather than fighting it later from InputProxy's connection errors. Exact port list and defaults can shift between image versions — confirm against Solace's current quick-start docs if anything above doesn't match what you pull.
03Bridge broker A to broker B

This is the hop that matters: a broker-to-broker bridge whose connection runs across the exact same shaped, flooded link everything else in this demo shares.

From Broker B's Manager (receiver side) — the consuming side is where the subscription that pulls messages across should live:

  1. Message VPN default → Bridges → Create Bridge.
  2. Remote broker address: $IP_SRC_PRIV:55555 (Broker A's private IP, reached across the shaper).
  3. Remote message VPN: default. Credentials: the admin user (or a dedicated bridge user if you create one).
  4. Add a remote subscription for topic channel/1 — this is what tells Broker A "forward anything published on this topic to me."
  5. Save, then confirm the bridge shows Up and the subscription is listed active. It should come up even under load once running — Solace bridges reconnect and resynchronize automatically after a drop.
Why the receiver side owns the bridge In pub/sub, demand flows from the consumer. Broker B is the one that wants channel/1, so it's the one that reaches out and declares that subscription across the bridge. Broker A never needs to know about Broker B in advance — it just serves whatever subscriptions arrive.
04Build BroadcastMe

The InputProxy/OutputProxy pair from Solace's live-streaming sample — unmodified. It only needs an argument choice (persistent vs. direct delivery), not a code change.

source + receiver $
git clone https://github.com/roberthatwork/broadcastme.git
cd broadcastme
./gradlew assemble

Built binaries land in build/staged/bin/ as inputProxy and outputProxy on both hosts — each host only ever runs the one it needs.

05Wire both paths, side by side

Two independent pipelines on the same hosts: the direct path from the base runbook, unchanged, and a second one that goes through the brokers. Both stream the same source clip at once.

PathSource emits toReceiver listens on
Direct (base runbook)udp://$IP_RCV_PRIV:5004udp://0.0.0.0:5004
Via Solaceudp://localhost:1235 (InputProxy)udp://0.0.0.0:1239 (from OutputProxy)

Receiver — bring up the broker-facing plumbing first, then both viewers:

receiver $ (terminal 1)
./build/staged/bin/outputProxy $IP_RCV_PRIV:55555 default default channel/1 127.0.0.1 1239 verbose
receiver $ (terminal 2)
ffplay -fflags nobuffer udp://0.0.0.0:5004   # Direct UDP window
receiver $ (terminal 3)
ffplay -fflags nobuffer udp://0.0.0.0:1239   # Via Solace window

Drag the two ffplay windows side by side (over VNC/RDP, or whatever desktop you're presenting from) and label them — "Direct UDP" and "Via Solace" — before anyone's watching.

Source — start InputProxy, then both ffmpeg processes:

source $ (terminal 1)
./build/staged/bin/inputProxy $IP_SRC_PRIV:55555 default default channel/1 persistent 1235 verbose
source $ (terminal 2)
ffmpeg -re -stream_loop -1 -i clip.mp4 -an -c:v libx264 -preset veryfast \
  -tune zerolatency -b:v 200k -f mpegts udp://$IP_RCV_PRIV:5004
source $ (terminal 3)
ffmpeg -re -stream_loop -1 -i clip.mp4 -an -c:v libx264 -preset veryfast \
  -tune zerolatency -b:v 150k -f mpegts udp://localhost:1235

Confirm both windows play clean before touching iperf3 — slower to start than a single stream would be, but smooth and unbroken in both. If either one isn't clean here, the comparison in Phase 07 won't read clearly.

Known limitation, not a blocker here OutputProxy binds to a temporary queue, which is torn down if its connection to Broker B ever drops. That matters for a full connection blackout on the receiver side — it doesn't matter for this demo, since the flood in Phase 07 congests the bridge between the brokers, not the receiver's local connection to Broker B. Worth a real durable-queue upgrade before staging the blackout scenario from the base runbook.
06Inject & compare

One flood, started once, hits both pipelines at the same instant — that simultaneity is the whole argument.

receiver $
iperf3 -s
source $ (new terminal)
# 10 Mbps against a 768 kbit ceiling — well past both video streams combined
iperf3 -c $IP_RCV_PRIV -u -b 10M -t 300
shaper $
watch -n1 tc -s qdisc show dev eth0

What to expect, and what to point at when it happens: the Direct UDP window stalls and stays broken — those frames are gone. The Via Solace window also stalls in real time (that's genuine backpressure, not staged), but once the flood stops the buffered packets held in Broker A's spool flush through as a rapid catch-up burst rather than a permanent gap. Same network event, two different outcomes — that contrast is the demo.

07Rehearse & tear down

Run it twice end to end before anyone's watching, then know how to shut off everything this phase added.

Go / no-go, before you present:

  • Bridge shows Up in Broker B's Manager before each run
  • Both windows play clean, side by side, with nothing else running
  • 10 Mbps flood visibly freezes the Direct window every time
  • Via-Solace window stalls, then visibly catches up once the flood stops
  • tc rules re-applied if the shaper was stopped/started since Phase 01
  • Recorded a clean backup run, in case the live link misbehaves in front of the audience

Tear down this phase's additions first — the base runbook's AWS teardown script handles the VPC, subnets, and instances unchanged and doesn't need any edits.

source $
pkill -f inputProxy; pkill -f ffmpeg
docker stop broker-a && docker rm broker-a
receiver $
pkill -f outputProxy; pkill -f ffplay
docker stop broker-b && docker rm broker-b

Then run the base runbook's Phase 05 teardown as-is to remove the instances, security group, route tables, subnets, and VPC.

Second document in the series — the base Tactical Link Runbook stays the "without Solace" reference; this one is "with." Stretch goal if there's schedule room: swap OutputProxy's temporary queue for a durable one so the guarantee also survives a receiver-side disconnect, not just bridge-level congestion.
