AWS + Solace · Complete Build · Rev. 5

Tactical Field Manual

One document, start to finish: a shaped and flooded network link, two Solace PubSub+ brokers bridged across it, and a direct-UDP video stream running side by side with an RTSP stream carried over Solace — so the same network flood produces two different outcomes.

Rev. 5 — corrects the bridge's video subscription to what was actually verified working end to end: s/v/c01/> crosses as a Guaranteed queue subscription, not Direct. Documents the real fixes it took to get there (a bridge Remote Message VPN address that must be a real IP, not an unresolvable v:<name>; persistent broker storage; a browser-facing RTSP bridge with an RTMP-push workaround for a legacy codec-mislabeling bug unrelated to Solace). Part Three's track generator and viewer are now a parameterized, multi-site publisher and a Solace-branded live fusion map with exact-match geofencing and clickable camera markers. Adds Part Two: real-time drone detection running against the resilient feed. Base link unchanged from Tactical Link Runbook.

Why this exists

A live camera feed sent as plain UDP video has no way to recover from a bad network moment — a burst of loss corrupts the decoder's reference frames and the picture freezes for good, even after the network recovers. This build puts that exact failure next to its fix, side by side, on the same link: the same camera feed, published once, carried to a second site over a Solace PubSub+ bridge using Guaranteed Messaging. Under identical injected congestion, the plain UDP window locks up permanently. The Solace-carried window stalls too — briefly — then catches up and keeps playing, because Solace held the video at the source until the link could take it again.

Everything here runs on off-the-shelf pieces: Solace's own PubSub+ broker container, its rtsp2solace/solace2rtsp reference images, and standard Linux traffic-shaping tools. Part One is a complete, self-contained demo buildable in about a day. Part Two adds real-time AI object detection running directly against the resilient feed — the point being that guaranteed delivery isn't just about a clean picture, it's what keeps a live detection pipeline actually seeing anything once the network gets bad.

Objective

02Shape the link

Cap the shaper's egress to a tactical-radio-like ceiling, sized for two video streams running at once, and add delay, jitter, and loss with netem.

shaper $
export IFACE=$(ip -o -4 route show to default | awk '{print $5}')
echo $IFACE   # ens5 on most current-generation instance types, not eth0

sudo tc qdisc replace dev $IFACE root handle 1: htb default 10
sudo tc class add dev $IFACE parent 1: classid 1:10 htb rate 768kbit ceil 768kbit
sudo tc qdisc add dev $IFACE parent 1:10 handle 10: netem \
  delay 100ms 20ms 25% distribution normal loss 2% 25%

tc -s qdisc show dev $IFACE
Note The 25% after the jitter value correlates each packet's delay with the one before it. Without it, video's bursty packets — several UDP datagrams per frame, sent within milliseconds of each other — can arrive out of order purely from independent random jitter, even with near-zero actual loss, and MPEG-TS continuity counters treat reordering the same as a drop. This correlation term keeps the shaping realistic for video traffic specifically, not just for a simple throughput test.
Why 768 kbit This build runs a direct video stream and a Solace-carried one at once. 768 kbit gives both comfortable headroom under normal conditions, so the flood in Phase 06 — not ordinary two-stream contention — is what causes the freeze.

Reset any time with sudo tc qdisc del dev $IFACE root. For the intermittent half of DIL — comms windows that drop out entirely rather than just degrading — toggle to full loss on a timer:

shaper $
cat <<'EOF' > ~/blackout.sh
#!/bin/bash
IFACE=$(ip -o -4 route show to default | awk '{print $5}')
while true; do
  sudo tc qdisc change dev $IFACE parent 1:10 handle 10: netem delay 100ms 20ms 25% loss 2% 25%
  sleep 45
  sudo tc qdisc change dev $IFACE parent 1:10 handle 10: netem loss 100%
  sleep 8
done
EOF
chmod +x ~/blackout.sh
Watch for tc rules do not survive a reboot or a stop/start cycle — reapply them before any rehearsal if the shaper instance restarted for any reason.

Watch for — disk space Both broker containers, plus every image this build pulls (mediamtx, ffmpeg, the cascades, and later rtsp_bridge), share the instance's root volume. A docker pull failing mid-layer with no space left on device is a real, recurring failure mode on the default 8–20 GB root volumes — check with df -h and docker system df before troubleshooting anything else looks broken, and reclaim space with docker image prune -a. When a new pull isn't possible, an already-pulled image's binary can usually stand in for a diagnostic tool: docker exec <existing-container> ffmpeg -i <url> works for a codec check without pulling anything new (see Phase 11C).

04The bridge

One bridge, two directions: it carries the RTSP DESCRIBE request from the sink to the source and the reply back as Direct messages, and the video itself as a Guaranteed queue subscription. The sink's own Guaranteed queue, created in Phase 03, is what actually rides out the shaped link's loss once the video arrives.

Corrected in Rev. 5 Earlier revisions of this manual put s/v/c01/> under Incoming Direct alongside the handshake topics. That's not what was actually verified working: a live, end-to-end test this build only started passing video once s/v/c01/> was moved to an Incoming Guaranteed subscription bound to a named queue. Follow the steps below, not the Direct-only version.

On Broker A's Manager (source): create the bridge that points at Broker B.

  1. Message VPN default → Bridges → Create Bridge. Name: bridge-to-b.
  2. Remote broker address: $IP_RCV_PRIV:55555 — the actual private IP, not a hostname. Remote message VPN: default. Credentials: ${BRIDGE_SVC_USER} / ${BRIDGE_SVC_PASS}.
  3. Save, then open the bridge's Subscriptions tab → Incoming Direct → add s/v/c01/desc. This is the RTSP DESCRIBE request the sink publishes on Broker B; Broker A needs to receive its own copy to answer it.

On Broker B's Manager (receiver): create the mirror-image bridge that points back at Broker A.

  1. Message VPN default → Bridges → Create Bridge. Name: bridge-to-a.
  2. Remote broker address: $IP_SRC_PRIV:55555 — the actual private IP, not a hostname. Remote message VPN: default. Credentials: ${BRIDGE_SVC_USER} / ${BRIDGE_SVC_PASS}.
  3. Save, then open the bridge's Subscriptions tab → Incoming Direct → add #P2P/> (the reply the source sends back to the sink's own dynamically-generated reply topic).
  4. Same bridge, Incoming Guaranteed tab → add subscription s/v/c01/>, queue name bridge2bQ. This is the video and audio topic; carrying it Guaranteed instead of Direct is what actually survives the shaped link's loss.
  5. Confirm both bridges show Up on their Summary tab, and specifically check the Details tab of each direction: a real remote address and a non-zero, growing uptime. A direction stuck at Remote Address: 0.0.0.0:0 with Uptime: 0d 0h 0m 0s is not actually connected even if the Summary tab briefly shows Up.
Note Use #P2P/>, not the narrower router-specific reply topic Broker Manager may show under a live session — the router name a reply topic is scoped to is derived from the container's own id and changes every time sink_cascade's container is recreated. The generic form keeps working across restarts.
Watch for Each of these topics should cross the bridge by exactly one mechanism — Direct or Guaranteed, never both. If a topic is reachable by two different paths across the same bridge, the far side receives two copies of every message, which surfaces as a stuck or stuttering picture on the sink even though delivery itself looks perfectly healthy on every broker statistic.
Watch for — the VPN address footgun Broker Manager can auto-populate a bridge's Remote Message VPN connection with an unresolvable internal virtual-router identifier that looks like v:<hash> instead of a real address. A bridge configured this way never actually connects, even though the UI may not make that obvious at a glance — the tell is the Details tab showing 0.0.0.0:0 and zero uptime. Fix it by explicitly setting the remote connection to the peer broker's real private IP, as in the steps above.
Note — transient endpoint error While a bridge direction is down, repeated failed RTSP handshake attempts can pile up temporary/non-durable endpoints faster than they expire, surfacing as No More Non-Durable Queue or Topic Endpoint in the logs. This is a symptom of the outage, not a separate bug — it clears on its own a few minutes after the bridge and handshake are actually working again.

Confirm the handshake works end to end before moving on: on the receiver, run a quick RTSP probe against the sink and watch its logs.

receiver $

# in a second terminal:
ffmpeg -rtsp_transport tcp -i rtsp://localhost:8554/c01 -c copy -f mpegts "udp://127.0.0.1:6004?pkt_size=1316"

06Inject & compare

One flood, started once, hits both pipelines at the same instant — that simultaneity is the whole argument.

receiver $
iperf3 -s
source $ (new terminal)
export IP_RCV_PRIV=10.0.3.x   # from Phase 00's table, if this session doesn't have it yet
# 10 Mbps against a 768 kbit ceiling — well past both video streams combined
iperf3 -c $IP_RCV_PRIV -u -b 10M -t 300
shaper $
export IFACE=$(ip -o -4 route show to default | awk '{print $5}')   # if this session doesn't have it yet
watch -n1 "tc -s qdisc show dev $IFACE"

The Direct UDP window stalls and stays broken — those frames are gone for good. The Via Solace window stalls too, in real time, then catches up with a burst of held frames once the flood stops — the sink's non-durable queue on Broker B holds what the bridge delivers late rather than dropping it. Watch that queue's Consumers tab in Broker B's Manager during the flood to see delivery continue climbing even while the picture itself is stalled.

07Rehearse & tear down

#!/usr/bin/env bash
# track_gen.sh — simulated sensor/track publisher. A single drone roams across
# the combined coverage area of one or more "camera" sites — stand-ins for
# anything from a fixed CCTV camera to someone's phone on a carrier network
# filming the sky — and is only reported while at least one of them currently
# has it in range. As the drone moves between sites' coverage, the reporting
# `site` in the topic changes (a handoff) while `track_id` stays constant the
# whole time, and the drone can go briefly unreported in the gaps between
# coverage zones — no retained messages or special broker config required.
#
# Env vars (all optional, defaults shown):
#   SITE       site1        used only to name the DEFAULT camera roster below;
#                            ignored if CAMERAS is set explicitly
#   TRACK_ID   trk-042      track id, included in the JSON payload — constant
#                            across the whole run regardless of which camera
#                            is currently reporting it
#   LAT        32.7473      starting/roaming-center latitude (decimal degrees)
#   LON        -97.0945     starting/roaming-center longitude (decimal degrees)
#   ALT        450          starting altitude, meters
#   CAMERAS    (see below)  camera roster as a Python literal list of
#                            (name, lat, lon, range_m) tuples. Defaults to
#                            three points scattered ~1-1.5km around LAT/LON,
#                            each with an 800m detection range, so a default
#                            run already demonstrates handoffs and coverage
#                            gaps. Example custom roster:
#                            CAMERAS="[('phone-1',32.7473,-97.0945,600),('phone-2',32.7540,-97.1020,900)]"
#   MARGIN_M   500          how far past the outermost camera's own coverage
#                            edge the drone is still allowed to roam before
#                            being steered back toward the roster's centroid
#   CELL       0.01         geo-cell size in degrees — MUST match the map's
#                            Cell Size field exactly or the geofence won't
#                            catch this track
#   BROKER     localhost    MQTT broker host
#   PORT       1883         MQTT broker port
#   RATE       1            publish interval, seconds (also the simulation
#                            step interval)
#
# Publishes to: sensor/track//cell//
#   Nothing is published for a step where no camera currently covers the
#   drone — the map's own dead-track pruning shows that as the track going
#   stale, then reappearing once a camera picks it back up.

TRACK_ID="${TRACK_ID:-trk-042}"

ALT="${ALT:-450}"

import os, math, random, subprocess, datetime, ast, sys, time

SITE = os.environ["SITE"]; TRACK_ID = os.environ["TRACK_ID"]
LAT = float(os.environ["LAT"]); LON = float(os.environ["LON"])
ALT = float(os.environ["ALT"]); MARGIN_M = float(os.environ["MARGIN_M"])
CELL = float(os.environ["CELL"]); BROKER = os.environ["BROKER"]
PORT = os.environ["PORT"]; RATE = float(os.environ["RATE"])

cameras_raw = os.environ.get("CAMERAS", "").strip()
if cameras_raw:

else:

        (SITE + "-cam1", LAT, LON, 800.0),
        (SITE + "-cam2", round(LAT + 0.0070, 6), round(LON - 0.0080, 6), 800.0),
        (SITE + "-cam3", round(LAT - 0.0060, 6), round(LON + 0.0090, 6), 800.0),
    ]

def meters(lat_a, lon_a, lat_b, lon_b):
    dlat_m = (lat_a - lat_b) * 111320.0
    dlon_m = (lon_a - lon_b) * 111320.0 * math.cos(math.radians(lat_b))
    return math.hypot(dlat_m, dlon_m)

centroid_lon = sum(c[2] for c in cameras) / len(cameras)
operating_radius = max(meters(c[1], c[2], centroid_lat, centroid_lon) + c[3] for c in cameras) + MARGIN_M

print("track_gen: %d camera(s) in roster, roaming radius ~%.0fm around (%.5f, %.5f)" % (
    len(cameras), operating_radius, centroid_lat, centroid_lon), file=sys.stderr)
for c in cameras:
    print("  camera %-16s (%.5f, %.5f) range %.0fm" % (c[0], c[1], c[2], c[3]), file=sys.stderr)

lat, lon = LAT, LON
heading = random.uniform(0, 360)
speed = random.uniform(15, 40)

while True:
    heading = (heading + random.uniform(-8, 8)) % 360
    speed = max(5, min(60, speed + random.uniform(-2, 2)))

    dist_from_centroid = meters(lat, lon, centroid_lat, centroid_lon)
    if dist_from_centroid > operating_radius:
        east = -(lon - centroid_lon) * math.cos(math.radians(centroid_lat))
        north = -(lat - centroid_lat)
        bearing_home = math.degrees(math.atan2(east, north)) % 360
        heading = (bearing_home + random.uniform(-20, 20)) % 360

    dist_deg = speed * RATE * 0.00003
    dlat = dist_deg * math.cos(math.radians(heading))
    dlon = dist_deg * math.sin(math.radians(heading)) / math.cos(math.radians(lat))
    lat = round(lat + dlat, 7)
    lon = round(lon + dlon, 7)

    covering = None; best_dist = None
    for (name, clat, clon, crange) in cameras:
        d = meters(lat, lon, clat, clon)
        if d <= crange and (best_dist is None or d < best_dist):
            covering = (name, clat, clon); best_dist = d

    ts = datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ")
    confidence = round(random.uniform(0.75, 0.99), 2)

            '{"site":"%s","track_id":"%s","lat":%s,"lon":%s,'
            '"home_lat":%s,"home_lon":%s,"alt_m":%s,"speed_mps":%s,'
            '"heading_deg":%s,"confidence":%s,"ts":"%s"}'
        ) % (cam_name, TRACK_ID, lat, lon, cam_lat, cam_lon, ALT, speed, heading, confidence, ts)
        topic = "sensor/track/%s/cell/%d/%d" % (cam_name, lat_idx, lon_idx)
        subprocess.run(["mosquitto_pub", "-h", BROKER, "-p", PORT, "-t", topic, "-m", payload], check=True)
        print("-> %s  %s" % (topic, payload))

    time.sleep(RATE)

The one rule that matters CELL here and the live map's Cell Size field (Phase 11B) must be exactly equal, not approximately. Both sides compute a cell index as floor(coordinate / CELL); even a small mismatch (say, 0.01 here vs. 0.01016 on the map) produces a completely different index for nearly every coordinate, not just at the edges — it reads as "the geofence loses the track" when the actual cause is two sides doing the same math with two different numbers. Default 0.01 on both ends unless you have a specific reason to change it.
Why no retained camera roster A cleaner design would have each camera announce itself once via a retained MQTT message, so every camera pin shows up on the map immediately on connect. That needs retained-message support enabled on the Solace side, which this build doesn't turn on. Instead, a camera simply appears on the map the same way a track always has — by publishing — the moment it actually has something to report. That also happens to fit the cover story better: a witness's phone isn't a pre-registered sensor, it only "exists" to the fusion picture the moment it captures something.

A Solace-branded browser page that subscribes to the cell-topic scheme from Phase 11 directly, plots every active track on a live map, lets you draw a geofence to filter what it subscribes to, and gives each simulated site a clickable camera marker.

This is a single self-contained HTML file, track-fusion-map.html, opened locally in a browser (file://…) — no server or build step. It uses Leaflet with Esri's World Dark Gray basemap, the Leaflet.draw plugin for geofencing, and MQTT.js over WebSockets to talk to the broker directly from the page.

Geofencing: use Add Circle / Add Polygon / Add Rect to draw a shape on the map. The page computes which geo-cells overlap the shape, subscribes only to those cells' topics (capped by the Max Subs slider), and reports a Coverage Accuracy percentage from sub-sampling each included cell. A track that leaves the drawn shape is filtered out within a few seconds by the automatic dead-track pruning (stale after 3s, removed from the map after 10s of no updates) — there's no indefinite ghost marker left behind.

What actually feeds it, and why The straightforward design — point rtsp_bridge at rtsp://sink_cascade:8554/c01 and let MediaMTX pull it — does connect, but the resulting browser video is audio-only with a black picture. Tracing it with ffmpeg -i (reusing an already-pulled container's binary via docker exec rather than pulling a new image, per the Phase 03 disk-space callout) shows the video track reports as mpeg4 (Simple Profile) at every point in the pipeline — even the original pre-Solace rtsp://server:8554/mystream — despite the source ffmpeg command explicitly encoding H.264 (-c:v libx264). This is a pre-existing mislabeling in the legacy UDP-to-RTSP repackaging from Phase 00, unrelated to Solace or either cascade; browsers can't decode old MPEG-4 Part 2, while VLC and ffplay silently tolerate it, which is why it was never noticed before this feature needed browser playback.

The workaround used here bypasses that chain entirely: push a fresh, correctly-encoded feed directly into rtsp_bridge over RTMP, reusing the source's already-running reader container so nothing new has to be pulled or installed:

source $
docker exec -d ubuntu-reader-1 ffmpeg -re -stream_loop -1 -i src/video.mp4 -an \
  -vf scale=640:360 -c:v libx264 -preset veryfast -tune zerolatency \
  -pix_fmt yuv420p -profile:v baseline -b:v 200k \
  -f flv rtmp://$IP_RCV_PRIV:1935/c01
Watch for This starts a second, independent ffmpeg process inside reader, separate from the one already feeding Phase 00's direct-UDP comparison stream. It won't survive a reader restart, and must be stopped selectively (docker exec ubuntu-reader-1 pkill -f "$IP_RCV_PRIV") rather than a bare pkill ffmpeg, which would also kill the unrelated Phase 00 process. RTSP push (ANNOUNCE) to this same path can return 501 Not Implemented depending on the MediaMTX build; RTMP push is the more reliably supported option and is what's used above. Also confirm port 1935 is actually in rtsp_bridge's ports: list — a push to an unpublished port fails as a plain connection refused, easy to mistake for a MediaMTX configuration problem.

Once this is running, clicking any camera marker on the live map (Phase 11B) opens a working video panel — audio and picture both.
